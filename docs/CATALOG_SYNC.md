# 전국 장소 DB 수집과 정기 갱신

반영일: 2026-09-14. 이 문서는 `MAP_DISCOVERY.md`의 과거 장소 수집/검색 한도 설명을 대체한다.

## 데이터 범위

- 한국관광공사 국문 관광정보 `KorService2/areaBasedSyncList2`의 공개 목록을 DB에 저장한다. 공식 안내: https://www.data.go.kr/data/15101578/openapi.do
- 최초 확인한 공급자 공개 항목 수는 49,722건이다. 이후 증감할 수 있고, 관광지 외에 음식점·숙박·행사·여행 코스 등도 포함한다. 모두 고유하거나 숨겨진 관광지라는 의미는 아니다.
- 이름, 주소, 공급자 ID, 좌표, 대표 사진 URL, 분류, 지역 코드, 수정 시각을 저장한다. 사진 파일 자체를 대량 다운로드하지 않는다.
- 기존 복구 장소와 사용자 제보는 보존한다. 따라서 DB 공개 장소 수와 공급자 원본 건수는 다를 수 있다. 주소가 없어도 이름과 유효한 공급자 ID가 있으면 검색 대상이 되며, 유효한 좌표가 없는 항목은 지도에서 제외한다.
- 사진 이용조건은 해당 공공데이터/사진의 출처 및 이용허락 범위를 별도로 따라야 한다. 상세 설명, 반려동물·무장애 정보, 혼잡도는 각각 기존 상세 API와 캐시를 사용한다. 이 목록 수집만으로 모든 장소의 혼잡도나 세부 정보가 생기지는 않는다.

## 갱신 흐름

1. 최초 서버 시작 후 공개 전체 목록을 한 번에 500건씩 수집한다. 페이지를 처리한 뒤 최소 2초 간격을 둔다.
2. 페이지 저장과 다음 페이지 체크포인트를 동일 DB 트랜잭션으로 처리한다. 강제 종료나 DB 오류가 나면 해당 페이지부터 재시도한다.
3. 초기 수집 후 한국 시간 매일 오전 3시에 변경분을 갱신한다. 서버가 꺼져 있었으면 다음 실행 때 밀린 작업부터 이어간다.
4. 실제 API의 `modifiedtime=YYYYMMDD`는 지정 날짜의 수정 항목을 반환하는 것을 확인했다. 이전 작업 시작일의 이틀 전부터 이번 작업 시작일까지 날짜별로 조회한다. 빈 날짜도 처리하며 날짜/페이지 진행 상태를 DB에 기록한다.
5. 7일이 지나면 놓친 날짜별 변경분을 먼저 처리하고 공개 전체 목록을 다시 점검한다. 장기간 서버가 꺼져 있어도 비공개 전환 정보의 갱신 시점을 건너뛰지 않는다.

Spring의 앱 내부 스케줄러다. PC와 백엔드가 실행 중이어야 작동한다. Windows 서비스 등록, 자동 부팅 실행, 외부 운영 서버 배포는 이 변경에 포함하지 않는다.

## 안전장치

- 공급자 `contentid`에 고유 인덱스를 두고 기존 장소 ID를 유지한다. `oldContentid`로 ID가 변경된 항목도 기존 장소와 연결한다.
- 찜·후기·사용자 제보·관리자 승인 여부를 덮어쓰거나 삭제하지 않는다. 공급자 `showflag=0`을 확인하면 공개 조회만 차단한다. 원본과 사용자 연결 기록은 보존한다.
- 더 오래된 수정 시각의 응답은 최신 정보를 덮어쓰지 못한다. 전체 목록에서 일시적으로 보이지 않는다는 이유만으로 장소를 삭제하지 않는다.
- 응답 페이지/건수가 불완전하면 성공으로 처리하지 않는다. 저장 실패 시 페이지 전체를 되돌리고 1분부터 최대 1시간까지 재시도 간격을 늘린다.
- DB에 단일 수집 작업의 임대 잠금을 두어 같은 DB를 쓰는 서버 간 동시 수집을 막는다. 서버가 비정상 종료되면 최대 2분 후 잠금을 다시 확보할 수 있다.
- 목록 API 사용량은 한국 날짜 기준 DB에 기록하여 재시작 후에도 유지한다. 기본 하루 300회이며 `SOOMGIL_TOUR_CATALOG_DAILY_LIMIT`으로 조정한다. 한도 도달 시 다음 날 00:05 이후 재개한다.
- 이 한도는 목록 API용 로컬 제한이다. 상세/혼잡도 호출과 다른 프로그램의 동일 키 사용량까지 공급자 한도를 보장하지 않는다. 실제 키의 승인 한도에 맞춰 각각의 호출 예산을 설정해야 한다.
- API 키는 서버 `.env`/환경변수에만 둔다. 응답과 로그에 키·인증 URL·원본 예외 본문을 남기지 않는다.
- 공급자 목록은 시점 고정 스냅샷이 아니다. 수집 중 등록/수정이 일어나면 페이지 경계가 바뀔 수 있으므로 중복 ID 갱신, 날짜 중첩 수집, 주간 점검을 함께 사용한다.

## API와 화면

- `GET /api/places/search`: query, region, category, sort, page, size. DB 결과와 total/page/pageSize/hasMore를 반환한다. 기본 6건, 최대 60건이다. 검색어 별칭도 SQL 조건에 적용한다.
- `GET /api/places/nearby`: mapX, mapY, radius, category, sort, page, size. 좌표 인덱스로 사각 범위를 좁힌 뒤 실제 구면 거리로 반경 안만 조회한다.
- `GET /api/places/home`: 홈에 필요한 12건만 전달한다.
- 기존 `GET /api/places`는 배열 형식을 유지하되 페이지당 최대 60건으로 제한한다. 이 배열의 길이를 전국 총수로 사용하면 안 된다.
- 일반 검색과 지도는 외부 목록 API를 기다리지 않는다. 검색 페이지 제한을 없애고 전체 DB 후보를 순차 탐색할 수 있다.
- 혼잡도 카드도 지역 코드가 없다는 이유로 외부 목록 검색을 반복하지 않는다. 목록 메타데이터는 동기화 작업에서 갱신하고, 혼잡도 API에서 정확히 연결할 수 없는 장소는 미확인 상태를 유지한다.
- 혼잡도 필터는 24개 후보씩 예측을 확인하고 더 보기를 제공한다. 확인한 결과 수와 전체 후보 수를 구분한다. 미제공 값을 임의로 한적함/보통/붐빔으로 채우지 않는다.
- 지도는 60건씩 DB에서 확보하되 실제 화면에는 기존과 동일하게 최대 6개 카드/마커만 표시한다. 사용자 위치를 대신 승인하거나 저장하지 않는다.
- `GET /api/places/status`의 `sync`에 공개 수집 상태가 있다.
- 관리자 `/admin`의 **장소 데이터**에서 진행량, 공개 장소 수, 마지막 전체 수집/갱신 시각, 다음 실행, 오늘 사용량을 확인한다. 일시정지, 재개, 지금 갱신이 가능하다. 수집 중 갱신 버튼은 처음부터 재수집하지 않고 현재 위치를 이어간다.
- `GET/POST /api/admin/place-sync`는 관리자 세션이 필요하고 POST는 CSRF 검증을 적용한다. 회원이 쿼리나 본문에 관리자 코드를 넣어 접근할 수 없다.

## 운영과 보관

설정 예시는 루트 `.env.example`의 `SOOMGIL_TOUR_SYNC_ENABLED`, `SOOMGIL_TOUR_CATALOG_DAILY_LIMIT`을 참고한다. 수집을 비활성화하거나 API가 중단되어도 저장된 DB 검색은 가능하다.

실행 환경은 현재 파일 DB인 H2 (`backend/data/soomgil.mv.db`)다. 자동 테스트도 H2에서 검증하며 실제 MariaDB 운영 연결/성능 검증을 대신하지 않는다. 검색 텍스트는 정규화 컬럼과 바인딩된 LIKE 조건을 사용한다. 대규모 동시 접속 운영에서는 실행 계획·부하 측정 후 전문 검색 인덱스나 검색 엔진을 추가 검토한다.

DB 백업은 백엔드를 중지하고 파일을 복사한 뒤 SHA-256을 비교한다. 이번 작업의 C/D 백업 위치는 각각 프로젝트의 `backup/catalog-sync-20260914`다. `.env`와 DB는 소스 ZIP/Git bundle에 넣지 않는다. 실행 중인 D 프로젝트 DB를 덮어쓰지 않는다. 백업 ZIP에는 미커밋 소스도 들어가고 bundle에는 커밋 기록만 들어간다. 로컬/외장하드 백업은 GitHub 업로드와 다르다.

## 배포 확인 메모

첫 전체 수집과 DB 검색/지도 연결은 실행 중인 서버에 적용했다. 이후 추가한 이름 조회 인덱스 최적화, 주간 재점검 전 누락 날짜 우선 처리, 카드의 목록 재호출 제거는 최신 소스/JAR에 포함되어 있다. 실제 마지막 페이지에서 공급자가 numOfRows=500 대신 남은 실제 건수 222를 보고하는 것을 확인하여 해당 형식도 허용하되 실제 행 수는 계속 엄격히 검증하도록 수정했다.

사용자가 백엔드를 재시작한 뒤 2026-09-14 20:14:33(KST)에 첫 전체 수집이 완료됐다. 공급자 목록 49,722건을 처리했고 공개 DB 장소는 기존 장소를 포함해 49,731건이었다. 상태 API의 initialComplete=true, processed=49,722, state=waiting을 확인했다. 다음 예약 실행은 2026-09-15 03:00(KST)이다. 이 숫자는 해당 시점의 수집 결과이며 이후 갱신에 따라 달라진다. 완료된 49,731건 DB의 별도 파일 백업까지 완료했다는 의미는 아니다.

최종 검증: 백엔드 69개, 프론트 37개 테스트 및 프로덕션 빌드를 통과했다. 검색 페이지 이동, 혼잡도 후보 24건에서 48건 누적 조회, 지도 반경 3km/카드와 마커 6개 제한, 홈 추천 사진 4개 유지, 320/390/1280px에서 가로 넘침 없음을 확인했다. 실제 기기 위치 권한은 대신 승인하지 않았다. 운영 MariaDB와 다중 서버 부하 시험은 포함하지 않는다.
