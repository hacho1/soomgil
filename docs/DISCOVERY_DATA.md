# 탐색 데이터와 배지 확장

## 구성

- `frontend/src/data/categories.json`: 9개 대분류, 108개 소주제. 홈에서는 앞의 6개만 표시한다. 검색 필터에서는 9개 모두 사용한다.
- `backend/src/main/resources/data/search-keywords.json`: 주제 검색어, 전국 17개 시도별 검색어, 동의어 41묶음, 연관 주제 17묶음, 관광공사 요청용 키워드 매핑.
- `backend/src/main/resources/data/badges.json`: 24개 배지의 고정 ID, 활동 종류, 조건, 등급, 보상.

키워드·카테고리·동의어·연관 주제를 합쳐 띄어쓰기 중복을 제거한 기본 자동완성 후보는 383개다. 공개 승인된 DB 장소명도 후보에 추가된다. 네이버 등 외부 키워드 서비스를 호출해 수집한 자료는 아니며 직접 정리한 탐색 데이터다.

## 검색 규칙

`GET /api/suggestions?q=`는 최대 8개의 문자열을 반환한다. 정확히 일치, 접두어, 포함, 한글 초성/입력 중 음절, 동의어 순서로 정렬한다. 빈 입력에는 자동완성을 보내지 않고 화면에 최근 검색어만 표시한다. 취소된 요청의 늦은 응답은 반영하지 않는다.

`GET /api/suggestions/related?q=`는 최대 6개의 연관검색어를 반환한다. `바다 → 해변·해수욕장`은 검색 동의어지만, `바다 → 노을·바다 카페`는 사용자가 직접 선택하는 연관검색어다. 연관 주제를 검색 동의어에 섞지 않는다. `강릉바다`와 `강릉 바다`처럼 사전에 등록한 복합어의 띄어쓰기를 정규화한다.

카테고리 소주제와 전체 보기는 동일한 분류 조건을 적용한다. 주소에 특정 단어가 들어 있다는 이유로 장소 종류를 판단하지 않는다. 반려동물·무장애의 확인되지 않은 안내 문구는 검색 본문에서 제외한다. 동반/접근성 필터는 검증된 속성 데이터를 확보한 뒤 별도로 제공해야 한다.

카테고리 JSON은 Gradle `processResources` 단계에서 서버의 `data/categories.json`으로도 패키징한다. 수정 후 프론트 빌드와 백엔드 재빌드·재시작을 모두 해야 한다. 장소 목록은 관광공사에서 가져온 자료와 저장된 장소에 한정되므로 검색어를 추가해도 모든 주제의 결과가 반드시 생기지는 않는다. 캠핑 키워드는 야영 허가나 시설 운영 여부를 보증하지 않는다.

## 배지 규칙

- 기존 7개 배지의 ID, 획득 기록, 50 EXP 보상을 유지한다. 새로운 배지는 10~20 EXP로 보상하며 기존 레벨 기준은 바꾸지 않는다.
- 검색, 상세 열람, 찜, 후기, 다이어리, 제보 활동을 단계별로 구분한다. 상세 열람 배지는 실제 장소 방문 인증을 의미하지 않는다.
- 검색은 결과가 있는 서로 다른 검색어, 열람·찜·후기는 서로 다른 장소 기준으로 계산한다. 다이어리는 저장된 기록 ID 기준이다.
- 제보 승인 배지는 관리자 승인 시에만 부여한다. 반려 후 재승인해도 동일 제보에 대한 보상은 한 번이다. 획득 배지는 이후 기록 삭제나 승인 취소로 회수하지 않는다.
- 사용자별 DB 행 잠금과 활동/배지 고유 키로 중복 지급을 방지한다. 사용자 진행 상황 조회 시 기존 기록과 이전 승인 제보를 기준으로 새 배지 조건을 재평가한다.
- 프로필 전시는 획득 배지 중 0~1개만 가능하다. 다른 배지를 선택하면 교체하고 다시 선택하면 전시를 해제한다. 배지 화면에는 획득 여부, 활동 종류 필터, 구체적인 조건과 진행도를 표시한다.

## 확인

백엔드 `gradlew.bat test`로 검색 데이터, 지역/복합어, 공개 범위, 기존 배지 보존, 승인 전환, 동시 보상, 전시 제한을 검사한다. 프론트는 `npm.cmd test`와 `npm.cmd run build`로 검증한다. 데이터 JSON을 바꿀 때 테스트의 기대 개수도 실제 목표에 맞춰 검토한다.
