# 다이어리 저장 및 반복 요청 방어

## 적용 범위

2026-09-15 구현. 백엔드 재시작 후 적용된다. Caddy 설정은 배포 서버에 별도로 적용해야 한다. 운영 DB의 기록이나 사진을 삭제하지 않으며, 저장 용량 계산용 `storage_bytes` 컬럼과 사용자 조회 인덱스만 추가한다.

## 다이어리 검증

| 항목 | 기준 |
| --- | --- |
| API 요청 본문 | `/api/` 요청당 최대 4,500,000바이트. Content-Length가 없어도 읽는 중 제한. 압축 본문은 415로 거절 |
| 사진과 그림 | 각각 data URL 전체 2,000,000자 이하, 실제 JPEG/PNG/WebP 디코딩 확인 |
| 해상도 | 한 변 4,096px 이하 및 총 4,000,000픽셀 이하 |
| 동시 이미지 처리 | 서버 프로세스당 2개. 처리 중이면 429와 재시도 시간 반환 |
| 제목/본문/장소명 | 각각 150/3,000/200자 이하, 문자열만 허용 |
| 날짜/꾸미기 | 유효한 4자리 연도 날짜, 정해진 날씨·글꼴·레이아웃, 6자리 HEX 색상 |
| 배지 스티커 | 획득한 배지만, 최대 20개. 좌표 0~100, 배율 0.25~4, 회전 -360~360. 다른 필드 거절 |
| 계정별 저장 한도 | 기본 300개 및 합계 64MiB. 텍스트와 Base64 이미지의 UTF-8 바이트 합계이며 DB 물리 파일 크기가 아님 |

프로필 전시 배지 0~3개 제한과 다이어리 스티커 20개 제한은 별개다. 스티커 데이터의 서버 검증을 보강한 것이며, 이번 작업에서 그림·스티커 편집 UI를 추가한 것은 아니다.

`SOOMGIL_DIARY_MAX_ENTRIES`, `SOOMGIL_DIARY_MAX_BYTES`로 계정별 한도를 조절한다. 환경변수 변경 후 재시작한다. 이미 한도 초과인 기록도 삭제하지 않는다. 용량을 늘리지 않는 수정과 삭제는 허용한다. 계정 행 잠금과 트랜잭션을 사용하여 동시에 저장해도 한도를 초과하지 않게 한다.

기존 HTTPS 이미지 URL은 수정 전과 정확히 같을 때만 유지할 수 있다. 새 외부 URL은 받지 않고, 서버에서 사용자 URL을 다운로드하지 않는다. 기존 손상 이미지·잘못된 스티커 값은 저장 시 오류가 날 수 있으며, 원본을 자동 제거하지 않는다. 클라이언트 사진 업로드는 기존 캔버스 축소를 유지한다. 서버 검증은 이미지 재인코딩이나 모든 메타데이터 제거를 보장하지 않는다.

## 요청 횟수

| 기능 | 계정 또는 비로그인 IP별 기준 |
| --- | --- |
| 자동완성/연관어 | 합계 분당 240회 |
| 장소 검색/주변/탐색/홈/추천 | 합계 분당 120회 |
| 장소 상세/혼잡도/방문정보/후기 조회 | 합계 분당 240회 |
| 개인 다이어리/문의 조회 | 합계 분당 60회 |
| 다이어리 작성/수정 | 합계 10분당 30회 |
| 문의 작성/수정 | 합계 10분당 5회 |
| 후기 작성 | 10분당 10회 |
| 후기 좋아요 | 분당 60회 |
| 개인 다이어리/문의/후기 삭제 | 합계 10분당 60회, 저장 제한과 별도 |

요청이 처음 발생한 때 시작하는 고정 시간창이다. 요청 내용을 검사하기 전 횟수를 계산하므로 유효하지 않은 작성 시도도 포함한다. 로그인 계정별 제한에 더해 IP별로 위 기준의 5배를 적용한다. 공유 학교 네트워크의 정상 사용자 수에 따라 실측 후 조정해야 한다. 코드의 `ApiUsageLimits.rule`에서 횟수를 관리한다.

사용자는 세션에서, IP는 서버가 신뢰하는 원격 주소에서 얻는다. 쿼리의 `userId`와 임의 `X-Forwarded-For` 값으로 제한을 바꿀 수 없다. 배포 시 백엔드 포트는 루프백에 묶고 신뢰 프록시 설정을 유지해야 한다. 인증·메일·관리자 API의 기존 보안 정책은 별도로 유지한다.

횟수는 DB에 해시 키로 기록한다. 트랜잭션 실패나 서버 재시작으로 초기화되지 않는다. 초과 시 HTTP 429, `Retry-After` 헤더와 `retryAfterSeconds`를 반환한다. 화면은 오류와 대기 안내를 표시하며 쓰기 요청을 자동 재전송하지 않는다. 저장 실패 시 다이어리·문의 입력 상태를 초기화하지 않는 기존 처리를 유지한다. 용량 초과 413은 프록시가 일반 텍스트로 반환하더라도 안내 문구를 표시한다.

## 검증과 운영 한계

- 실제 JPEG/PNG/WebP, 위장 형식, 큰 해상도, 손상 이미지, 배지 소유권과 스키마 테스트.
- UTF-8 기존 기록 용량 계산, 초과 계정 수정, 삭제 후 재사용, 롤백, 동시 저장 테스트.
- 격리된 테스트 DB와 HTTP 서버에서 길이 지정/청크 전송 초과 요청의 413, 실제 API 429/Retry-After, 조회·삭제·다른 계정 분리 확인.
- API 클라이언트의 413/429 안내, 자동 재전송 없음, CSRF 유지 테스트.
- 실제 지리산 서버의 Caddy 적용, 공유 IP 부하 테스트, MariaDB 전환 검증은 별도다. 현재 테스트 DB는 H2다.
- 이 제한은 분산 DDoS 방어나 서버 전체 저장 공간 상한이 아니다. 운영 디스크 여유량 감시와 서버 앞단 방어가 필요하다.
- 다이어리는 아직 목록 조회에 이미지 원문을 포함한다. 기록 증가 시 목록 페이지네이션과 썸네일/원본 분리 저장을 추가하는 것이 좋다.
- 바이러스 검사, 서버 이미지 재인코딩, 보관 기간 정책은 이번 작업 범위 밖이다.
