# 이메일 인증과 계정 복구

## 현재 상태

Gmail SMTP 발송 코드와 가입/복구/이메일 변경 화면을 구현했다. 2026-09-15 사용자가 Gmail 연결 정상 동작을 확인했다. 이는 사용자 확인 결과이며 자동 테스트에서 실사용자에게 메일을 보낸 것은 아니다. 설정이 없으면 인증 요청은 503, 인증 없는 신규 이메일 가입은 400으로 거절한다. 기존 로컬 로그인과 Google/네이버 로그인은 유지한다. 설정이나 코드 변경 후에는 백엔드 재시작이 필요하다.

## Gmail 연결

1. 숨길 발송 전용 Gmail 계정에서 2단계 인증을 설정한다.
2. [Google 앱 비밀번호 관리](https://myaccount.google.com/apppasswords)에서 숨길 발송용 앱 비밀번호를 만든다. 일반 Google 로그인 비밀번호나 Google OAuth Client ID가 아니다. 앱 비밀번호 메뉴는 계정 정책에 따라 제공되지 않을 수 있다. [공식 안내](https://support.google.com/accounts/answer/185833?hl=ko)
3. 프로젝트 루트 `.env`에 아래 항목을 추가한다. 값은 채팅/스크린샷에 공유하지 않고 로컬 파일에서 입력한다. 앱 비밀번호의 표시용 공백과 따옴표를 넣지 않는다.

```properties
SOOMGIL_SMTP_HOST=smtp.gmail.com
SOOMGIL_SMTP_PORT=587
SOOMGIL_SMTP_USERNAME=발신계정@gmail.com
SOOMGIL_SMTP_PASSWORD=발급한앱비밀번호
```

`SOOMGIL_SMTP_FROM`은 생략하면 발신 계정을 쓴다. 별도로 지정할 때는 해당 계정 또는 Gmail에서 승인한 발신 별칭이어야 한다. STARTTLS 필수와 인증서 이름 검증을 적용했으며 연결/읽기/쓰기 제한 시간은 각각 5초다. 현재 설정은 587 STARTTLS용이며 포트만 465로 바꾸면 안 된다. [Google SMTP 문서](https://developers.google.com/workspace/gmail/imap/imap-smtp?hl=ko)

4. 실행 중인 백엔드를 정상 종료하고 `run-backend.cmd`로 다시 실행한다. 실행 중인 DB 파일을 복사하거나 다른 서버에서 동시에 열지 않는다.
5. `/api/auth/config`의 `emailVerificationAvailable=true`는 설정 존재 여부만 뜻한다. `/signupform`에서 본인 테스트 이메일로 인증번호를 요청하고 받은 번호로 인증/가입을 완료해야 실제 발송까지 검증된다.
6. `/recovery`에서 아이디 찾기와 비밀번호 재설정, 내 계정에서 이메일 변경을 확인한다. 재설정 후 다른 기기의 세션도 만료돼야 한다.

메일이 오지 않으면 스팸함, 발신 주소, 앱 비밀번호, Gmail 계정 정책, 587 outbound 연결을 확인한다. Google 계정 비밀번호를 바꾸면 앱 비밀번호가 취소될 수 있다. 원본 SMTP 예외나 비밀번호/인증번호를 운영 로그에 출력하지 않는다.

## 동작과 DB

- `POST /api/auth/email/request`: email, purpose. 목적은 signup/find-id/reset-password/change-email/verify-email.
- `POST /api/auth/email/confirm`: challengeId, code. 성공하면 10분짜리 일회용 proof를 반환한다. 프론트 메모리에만 보관하고 URL/localStorage에 넣지 않는다.
- 가입 `/api/auth/signup`, 아이디 찾기 `/api/auth/find-id`, 비밀번호 재설정 `/api/auth/reset-password`, 계정 이메일 변경에는 `emailProof`가 필수다. 목적/이메일/계정이 다르면 거절한다.
- 인증번호는 6자리 난수, 유효기간 10분, 잘못된 입력 최대 5회다. BCrypt 해시만 DB에 저장한다. proof도 SHA-256 해시로만 저장한다.
- 재전송 시 같은 목적의 이전 코드/인증 결과를 폐기한다. proof 소비와 실제 계정 변경을 같은 DB 트랜잭션에서 처리한다. 계정 변경 실패 시 proof 소비도 롤백된다.
- 복구는 사전에 인증한 이메일에만 보낸다. 미가입/미인증 이메일은 동일한 일반 응답을 반환하며 메일을 보내지 않는다. 공개 이메일/전화번호 가입 여부 조회는 제공하지 않는다. 가입 중복 안내는 이메일 소유를 인증한 뒤 제공한다.
- 예전에 미인증 이메일로 만든 계정은 로그인 후 `설정 → 내 계정 → 현재 이메일 인증하기`가 필요하다. 비밀번호를 이미 잊었다면 이메일만으로 자동 복구하지 않는다. 별도 신원 확인 절차가 마련되기 전까지 관리자도 임의 이메일 재지정이나 수동 비밀번호 발급으로 우회하지 않는다.
- Google/네이버 계정은 이 경로로 로컬 비밀번호를 만들 수 없다. 소셜 계정 연락처 변경은 이번 범위에 포함하지 않는다.
- 비밀번호는 기존 정책인 영문 대소문자, 숫자, 특수문자 포함 8~72자이며 BCrypt의 UTF-8 72바이트 제한도 적용한다.
- 비밀번호가 변경되면 기존 세션을 모두 폐기하고 재로그인을 요구한다. 변경 알림 메일도 발송 요청한다. 비밀번호나 임시 비밀번호를 메일로 보내지 않는다.
- `email_challenges`: 인증 목적/이메일/사용자/자격 증명 지문, 만료/시도/소비 상태. 매시간 하루 이상 지난 만료 자료를 삭제한다.
- `auth_rate_limits`: 해시 처리한 제한 키와 시도 횟수/만료. 실패 트랜잭션과 서버 재시작 후에도 제한을 유지한다.

## 호출 제한과 운영 주의

- 로그인: IP당 15분 30회, 계정당 15분 5회. 아이디와 이메일은 같은 계정 제한을 공유한다. 성공하면 계정 제한만 초기화하고 IP 제한은 유지한다.
- 현재 비밀번호 확인: 계정당 15분 5회. 성공하면 초기화한다.
- 인증 발송: IP당 15분 10회, 이메일당 60초 간격/시간당 5회, 전체 시간당 100회/하루 1,000회. 목적을 바꿔도 이메일 발송 제한을 공유한다.
- 코드 확인: IP당 15분 50회, 코드별 최대 5회 실패. 429 응답에는 Retry-After(초)가 포함된다.
- 제한의 기간은 요청 기준 고정 구간이다. Gmail 자체 할당량과 다른 앱의 발송까지 보장하는 값이 아니다.
- IP는 `request.getRemoteAddr()`를 사용하며 임의 X-Forwarded-For를 직접 믿지 않는다. Vite 프록시 개발 환경에서는 접속자가 같은 IP로 집계될 수 있다. 운영 리버스 프록시는 외부 전달 헤더를 제거/재설정하고, 서버에는 정확한 신뢰 프록시 주소만 등록한 뒤 실제 서로 다른 IP로 제한을 검증해야 한다. 무조건 모든 프록시를 신뢰하도록 바꾸지 않는다.
- SMTP 작업은 제한된 비동기 큐(대기 16개)로 처리한다. 발송 실패 시 인증을 폐기하고 서버에는 예외 종류만 기록한다. 큐는 영속 outbox가 아니므로 서버 중단 시 대기 메일은 유실될 수 있고 사용자가 재요청해야 한다. 대규모 배포 전에 발송 실패 모니터링, 영속 큐/재시도, 전용 발송 서비스와 도메인 인증을 검토한다.
- HTTPS, Secure 쿠키, 비밀키 재발급, 테스트 계정 정리, 실제 운영 DB 부하/백업 검증은 별도 출시 점검 항목이다. 이 작업만으로 전체 출시 준비 완료를 뜻하지 않는다.

## 검증 범위

메모리 H2와 테스트 메일 대역으로 가입/복구, 잘못된 코드 5회, 재전송, 만료, 목적/계정 불일치, 동시 소비/롤백, 이전 인증 무효화, SMTP 미설정/실패, 소셜 계정 우회 차단, 여러 기기 세션 폐기, 반복 로그인과 재시작 후 제한 유지를 검사한다. 테스트에서 실사용자 메일을 보내거나 파일 DB를 바꾸지 않는다. 실제 Gmail 수신과 운영 MariaDB 테스트를 대신하지 않는다.

2026-09-14 검증: 백엔드 83개/프론트 41개 테스트 및 양쪽 빌드 통과. 최신 JAR를 별도 메모리 DB/18080 포트에서 기동하여 health=true, SMTP 미설정 시 인증 요청 503을 확인한 뒤 종료했다. 320px 가입/계정 찾기, 390px 로그인, 1280px 로그인에서 가로 넘침이 없었고 브라우저 오류도 없었다. 이 UI 확인은 메일 미설정 상태이며 실제 코드 수신 후 화면 검증은 Gmail 연결 뒤 진행해야 한다. 기존 8080 서버와 실제 사용자 DB는 재시작/변경하지 않았다.
