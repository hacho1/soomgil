# 숨은 장소 추천 기준

## 2026-09-15 변경

후속 데이터 정리: `PLACE_DATA_QUALITY.md`를 따른다. 색인 버전 2부터 위치 정보의 충실도를 검색 순서에 반영하고 공식 여행 코스는 홈/주변의 개별 장소 추천에서 제외한다. 아래의 이전 측정값은 당시 데이터/규칙의 기록이다.

홈의 강원 고정 장소 4개, 사진 유무/이름 위주의 추천 정렬, 가장 가까운 2개를 그대로 제시하던 주변 추천을 변경했다. 장소 원본과 기존 혼잡도 계산식, 별점 값은 변경하지 않는다.

- 홈: 전국의 공개 장소에서 여행 취향·관심 지역·계절 키워드를 반영해 4곳까지 선택한다. 같은 지역과 여행 종류의 반복, 같은 이름·주소/근접 좌표의 중복, 이미 찜한 장소의 반복을 줄인다.
- 검색 추천순: 정확한 장소명은 항상 먼저다. 일반 장소명은 이름 시작/포함/연관어 순서를 유지한다. 등록된 넓은 주제어는 실제 장소 특성이 맞는 후보를 먼저 정렬한 뒤 취향·계절을 반영한다. 이름순과 지역/카테고리 필터, DB 결과 수는 유지한다.
- 주변: 실제 좌표가 있는 30km 안의 가까운 후보 최대 60개에서 2곳까지 선정한다. 원래 장소와 중복 항목은 제외한다. 거리와 취향, 여행 종류의 다양성, 확인된 당일 집중률 예측을 함께 반영한다.
- 함께 둘러볼 코스는 이 동일한 2곳을 재사용한다. AI가 이동 시간이나 운영시간을 확인한 반나절 일정은 아니다. 직선거리이며 도보/차량 경로 보장이 아니다.
- 배너: 추천 후보의 실제 관광공사 사진과 해당 장소 이름을 연결한다. 여행 종류가 다른 사진을 우선하고 오늘의 4곳과도 가능한 한 중복을 피한다. 사진이 없는 경우 임의 사진으로 장소를 꾸미지 않는다.
- 카드에는 최대 2개의 짧은 추천 근거를 표시한다. 상세의 추천 이유는 1곳에서만 보여준다.

## 데이터와 경계

`GET /api/places/recommendations` 응답은 `items`, `banners`, `season`, `date`, `personalized`, `method`다. 기존 `/api/places/home`은 목록 응답을 유지한다.

로그인 사용자의 선호는 세션의 본인 식별자로 읽는다. URL의 userId로 다른 사람의 취향을 요청하지 않는다. 사용자 식별자, 찜 ID 목록, 내부 점수는 응답하지 않는다. 공개 GET이어도 개인화 응답은 브라우저/프록시에 저장하지 않도록 기존 `no-store` 정책을 유지한다. 로그인·로그아웃·관심사 저장 시 이전 요청을 취소하고 홈이 표시될 때 추천을 다시 요청한다. 검색·지도·인증 화면에 직접 접속하면 불필요한 홈 추천을 함께 요청하지 않는다. 홈 위의 상세 팝업과 장소 상세 직접 접속의 홈 배경은 유지한다.

`user_settings.interests_json`과 `user_preferences`의 관심 지역·혼잡도 선호를 사용한다. 기존 한글 관심사도 ID로 정규화한다. 관심사가 없거나 비로그인이면 전국 추천이며, 위치 권한을 몰래 요청하지 않는다. 선호 지역은 필터가 아니라 우대 요소다. 홈에서 4곳이 반드시 같은 관심 지역에만 나오지는 않는다.

## 점수와 다양성

숫자는 내부 정렬 가중치이며 사용자 평점, 명소 인기도, 만족도 확률이 아니다.

| 근거 | 내부 가중치 |
| --- | --- |
| 산책/자연 카테고리 | +14 |
| 캠핑/문화 카테고리 | +8 |
| 숲길·둘레길·습지·생태·정원·계곡·해변·등대·고택 키워드 | +12 |
| 관심 여행 종류 일치 | +28, 여러 개 일치해도 한 번 |
| 관심 지역 일치 | +22 |
| 계절 관련 키워드 일치 | +6 |
| 관광공사 사진, 주소 존재 | 각 +2 |

홈/주변 후보를 최종 비교할 때 다음을 추가한다.

- 당일 집중률 예측이 40 미만이면 +22, 조용한 여행 선호라면 +32. 40~70 미만은 +4, 70 이상은 -30.
- 인기 있는 여행 선호는 당일 혼잡도만으로 강하게 배제하지 않으며 +8~10을 사용한다.
- 홈에서 이미 선택한 곳과 같은 지역이면 1곳당 -35, 같은 여행 종류면 1곳당 -24. 본인이 찜한 장소는 -32로 새 후보를 우선한다.
- 주변은 직선거리 1km당 -2, 같은 여행 종류의 반복은 -24. 출발지와 같은 종류는 -5다.

현재 또는 당일 확인이 없는 혼잡도는 **0점**이다. 자료가 없는 장소를 한적하다고 취급하지 않으며, 과거 보관 자료나 가짜/음수/999 값으로 한적함 가점을 주지 않는다. 검색 순서 자체는 혼잡도 새 조회가 끝날 때마다 바뀌지 않는다. 검색의 혼잡도 필터와 표시는 기존 집중률 조회 흐름을 사용한다.

집중률은 기존 방식인 `40 미만=한적함`, `40~70 미만=보통`, `70~100=붐빔`을 유지한다. 당일 캐시에 있는 값을 홈/주변 재정렬에 활용하며 추천 요청이 외부 API를 대량 호출하지 않는다. 캐시가 없는 곳은 화면에 표시된 장소부터 기존 제한 안에서 조회한다. 뒤늦게 붐빔/미확인으로 갱신되면 카드의 ‘오늘 한적함 예측’ 문구도 제거한다.

이 데이터만으로 ‘덜 알려진 곳’ 또는 실제 현장의 한적함을 입증할 수는 없다. 그래서 추천 문장에는 유명도·방문객 수·무료 주차·반려동물 가능·무장애 가능 등을 추측해서 넣지 않는다. 계절 키워드도 현재 개화·단풍·날씨를 보증하지 않는다.

## 성능과 일관성

- 전국 DB에서 지역과 여행 종류별 후보를 먼저 배분하고, 각 조합 최대 3곳·전체 최대 360곳만 메모리로 가져온다. 가장 큰 지역 하나가 후보 전체를 채우는 일을 줄인다.
- 동점 후보는 한국 날짜와 장소 ID 기준으로 순환한다. 동일 날짜·동일 취향·동일 데이터면 안정적인 순서를 유지한다. 후보가 적으면 날짜가 바뀌어도 같은 곳이 나올 수 있다.
- 최대 16종의 취향/지역 조합에 후보 ID와 내부 점수를 60초간 보관한다. 사용자 ID나 개인 찜 목록은 캐시하지 않는다. 재사용 때마다 DB에서 `approved=TRUE`, `tour_visible=TRUE`를 다시 확인하고 현재 공개 데이터로 응답한다.
- 신규 장소나 수정된 정렬 근거는 캐시 만료 후 반영될 수 있다. 비공개 전환은 캐시 만료를 기다리지 않는다. DB 장애 시 오래된 원본 데이터를 성공 응답으로 돌려주지 않는다.
- 장소의 기본 가중치·관심사·계절·여행 종류·주제 일치 여부를 DB 저장/갱신 때 미리 계산한다. 추천 조회에서는 긴 설명을 반복 비교하지 않고 정수와 별도 인덱스를 사용한다. 후보 선정에는 ID와 정렬용 필드만 사용하고 최종 최대 360개 원본을 별도로 읽는다.
- 같은 취향의 동시 캐시 미적중 요청은 하나의 후보 생성 작업을 공유한다. 잠금은 16개로 제한하고 실패 응답을 캐시하지 않는다. 날짜가 바뀌거나 60초가 지난 경우 다시 선정한다.
- MariaDB 실제 서버, 대규모 동시 접속, 외부 이미지 전송 속도는 별도 부하 검증이 필요하다. DB 쿼리 측정과 브라우저 전체 로딩 시간은 다르다.

## 주제 검색 규칙

`backend/src/main/resources/data/search-topics.json`에서 바다·산책·캠핑·카페·맛집·계곡·자연·산·박물관·전시·역사·공원 12개 주제의 정렬 근거를 관리한다. 자동완성/동의어 JSON은 그대로 두며 결과에서 항목을 삭제하는 필터가 아니다.

- `바다`/`해변`/`해수욕장`: 해변·해수욕장 등으로 끝나는 장소명을 우선한다. 장소명 뒤의 괄호 설명은 제외하고 비교한다. 펜션·음식점·캠핑장, 해변을 언급하는 여행 글이나 축제는 같은 우선 조건을 받지 않는다.
- `강릉 바다`, 사전에 등록된 `강릉바다`: 지역 검색 조건과 바다 주제 정렬을 함께 적용한다.
- `바다 카페`: 마지막 주제인 카페를 우선한다.
- `바다정원펜션`, `정동진해변`: 넓은 주제어로 오인하지 않으며 정확한 이름 일치를 유지한다. 실제로 이름이 `바다`인 장소도 정확한 일치이므로 먼저 나온다.
- 사진이 있거나 사용자가 카페를 좋아한다는 이유만으로 해변보다 펜션·카페가 먼저 나오지 않는다. 분야가 맞는 후보끼리는 기존 취향·계절 가중치를 사용한다.

이는 장소명/분류에 근거한 정렬이며 관광공사의 콘텐츠 종류 전체를 새로 분류한 것은 아니다. 여행 코스는 계속 검색할 수 있고, 공식 코스 종류를 별도로 저장·표시하는 기능은 이번 범위에 포함하지 않는다.

## 기존 DB 적용

재시작 시 `places`에 `discovery_base`, `discovery_interests`, `discovery_seasons`, `discovery_theme`, `discovery_topics`, `discovery_region`, `discovery_eligible`, `discovery_version`과 `places_discovery_idx`를 추가한다. 기존 행은 500개씩 트랜잭션으로 보정한다. 첫 실행은 보정 완료까지 시작 시간이 늘어날 수 있으며 도중 중단 시 미완료 행을 다음 실행에 이어서 처리한다. 이후 시작은 버전을 확인하고, 장소 수집·제보 수정은 기존 `PlaceQueries.index` 경로로 바로 갱신한다. 원본 장소, 계정, 찜, 후기, 다이어리를 삭제하지 않는다.

주제 JSON 순서/규칙 또는 `DiscoveryRecommendations.indexValues` 계산식을 바꾸면 `INDEX_VERSION`도 올려야 기존 데이터가 재계산된다. 관심사 비트 순서와 계절 순서(봄·여름·가을·겨울)도 같은 버전 관리 대상이다. `approved`/`tour_visible`은 DB 인덱스와 최종 원본 조회에서 현재 값을 확인하므로 비공개 변경을 캐시 만료까지 기다리지 않는다.

## 검증

정확한 장소명 우선, 필터 경계 유지, 지역 다양성, 날짜 순환, 찜 중복 완화, 근접 중복 제거, 30km/2곳 제한, 코스와 주변 목록 일치, 현재/과거/없는 집중률 분리, 사용자 간 취향 분리, 캐시 공개 상태 재검증, 기존 관심사 전체 대응을 테스트한다. 기존 인증/DB/관리자 테스트도 함께 실행한다.

2026-09-15 1차 확인 결과(후속 최적화 이전 기준):

- 백엔드 106개, 프론트엔드 45개 테스트 통과. `bootJar`와 프론트 배포 빌드 성공.
- 사용자 재시작 후 실제 추천 API 응답 확인: 홈 4곳, 배너 3곳, 두 목록 사이 중복 0곳. 로그인 화면에서는 기존 산책 취향을 반영하며 개인 설정을 변경하지 않고 확인했다.
- `가좌산대나무숲길` 이름 검색은 해당 장소 1건, `바다` 검색은 전국 887건으로 응답했다. 건수는 검증 당시 DB 기준이다.
- 320px/390px 모바일과 1280px 데스크톱에서 홈·검색 카드의 가로 넘침을 확인했다. 긴 배너 제목과 버튼이 겹치지 않았으며 상세 추천 이유 1곳, 주변 추천 2곳을 확인했다.
- 상세 확인으로 최근 본 목록에 같은 장소가 추가되더라도 홈의 추천 근거가 사라지지 않도록 수정하고 회귀 테스트를 추가했다.
- 실제 DB의 캐시 미적중 조회는 약 5~10초, 즉시 재조회는 약 0.34~0.37초였다. 빌드/테스트를 함께 실행한 개발 PC 측정이다. 첫 응답과 동시 요청 성능은 운영 전 개선·부하 검증이 필요하다.

위에서 발견한 첫 조회 속도와 일반 주제 정렬은 후속 최적화 대상으로 반영했다. 혼잡도 미제공/조회 지연은 실측값을 만들어 채우지 않는다.

2026-09-15 후속 최적화 검증:

- 백엔드 111개 테스트 통과(실제 백업 성능 테스트 포함, 생략/실패 0개), 프론트엔드 46개 통과. `bootJar`와 프론트 배포 빌드 성공.
- 검증된 49,754개 장소의 H2 파일 DB 백업을 임시 디렉터리에 복원해 확인했다. 기존 DB는 열거나 수정하지 않았다. 장소 수는 보정 전후 동일했다.
- 최초 일괄 보정은 약 68초였다. 실제 실행 중인 PC 상태에 따라 첫 시작에 1~2분 이상 걸릴 수 있다. 이후에는 완료된 버전의 행을 다시 보정하지 않는다.

# 추천 정책 2차 보완 (2026-09-15)

- `discovery-rules-v2`: 홈과 주변 추천은 이름·주소·국내 유효 좌표를 먼저 확인합니다. 공식 여행코스(25), 숙박(32), 쇼핑(38), 축제·행사(15)는 자동 탐방 추천에서 제외하고 일반 검색에서는 유지합니다. 행사 운영일을 확인하지 않은 상태에서 상시 탐방지처럼 제시하지 않습니다.
- 기존 공식 유형 미확인 자료는 주소·좌표가 충분하면 후보로 유지합니다. 실제 장소 검증 완료나 숨겨진 정도를 인증한다는 의미는 아닙니다. 다음 관광공사 메타데이터 갱신에서 유형이 확인되면 해당 기준을 적용합니다.
- 추천의 SQL 색인과 실시간 점수 모두 공식 유형으로 정규화한 카테고리를 사용합니다. 색인 버전 3으로 처음 시작할 때 재계산합니다.
- 주변 추천은 적합성 조건을 SQL에서 먼저 걸고 최대 60개를 조회하므로 가까운 숙소가 많아도 적합한 후보 2개를 밀어내지 않습니다. 최대 30km, 같은 장소 중복 제외, 실제 후보가 부족하면 2개를 억지로 채우지 않습니다.
- 추천 이유에 주변 장소와의 직선거리를 추가합니다. 최신 집중률이 확인된 때만 오늘 혼잡도 예측을 활용하며 자료 부족은 한적함으로 치환하지 않습니다. 신규 AI 호출은 없습니다.
- 배너는 이름·주소/좌표 중복도 확인합니다. 후보가 충분하면 오늘 추천과 다른 장소를 우선하며 동일 지역으로만 고정하지 않습니다.
