# 지리산 서버 배포 준비

## 확인한 내용

- 사용자 지정 서버: Windows, `jiri.hknu.ac.kr`, `220.68.241.128`.
- 2026-09-15 로컬 DNS 조회에서 A 레코드가 해당 IP와 일치했습니다. HTTPS 연결, 인증서, 서버 접속 권한은 아직 확인하지 않았습니다.
- 이 작업은 로컬 소스와 배포 준비 파일만 변경했습니다. 학교 서버 접속, 서비스 설치, 방화벽 변경, 파일 업로드는 하지 않았습니다.
- **전용 서버인지 공유 서버인지 먼저 확인**해야 합니다. 아래 루트 도메인 구성은 숨길이 해당 호스트를 전용으로 사용하는 경우에만 적용합니다.

## 접속 주소 결정

전용 호스트를 사용하도록 학교에서 승인한 경우:

| 항목 | 값 |
| --- | --- |
| 웹 주소 | `https://jiri.hknu.ac.kr` |
| 네이버 서비스 URL | `https://jiri.hknu.ac.kr` |
| 네이버 Callback URL | `https://jiri.hknu.ac.kr/api/auth/naver/callback` |
| 구글 승인된 JavaScript 원본 | `https://jiri.hknu.ac.kr` |
| 관리자 화면 | `https://jiri.hknu.ac.kr/admin.html` |
| 백엔드 내부 주소 | `127.0.0.1:8080` |

구글은 현재 JavaScript 콜백으로 받은 ID 토큰을 백엔드에 보내는 구성입니다. 네이버 콜백 주소를 구글 Redirect URI에 복사하지 않습니다. 제공자 콘솔에서 서비스 공개/검수 상태와 테스트 사용자 제한도 확인해야 합니다. [구글 설정](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid), [네이버 설정](https://developers.naver.com/docs/login/devguide/devguide.md).

공유 서버라면 기존 IIS/Caddy/Nginx와 다른 학생 서비스의 80/443/8080을 점유하거나 덮어쓰지 마세요. 학교가 지정한 전용 서브도메인 또는 프록시 연결 지점을 먼저 받습니다. `/soomgil` 같은 하위 경로는 현재 루트 기반 라우팅/API/쿠키와 다르므로 바로 적용하지 말고 별도 수정·검증해야 합니다. 지정 포트가 있다면 HTTPS 프록시와 백엔드 운영 검증의 포트도 함께 검토합니다.

## 설치 전

1. 서버에 Java 17과 빌드된 JAR/`frontend/dist`를 준비합니다. Node는 서버에서 프론트를 빌드할 때만 필요하며 Vite 개발 서버는 공개하지 않습니다.
2. 학교 승인 후 기존 `deploy/Caddyfile`, `deploy/windows/*.xml`을 검토합니다. [Caddy HTTPS 조건](https://caddyserver.com/docs/automatic-https)에 맞는 DNS, 인증서 발급, 80/443 연결이 필요합니다. 이미 학교 TLS 프록시가 있으면 학교 구성에 맞춥니다.
3. `deploy/windows/jiri.settings.example`은 **자동 적용되지 않는 참고 템플릿**입니다. 서버의 비공개 `.env`에 적용할 값을 검토합니다. API 키, Gmail 앱 비밀번호, 관리자 아이디는 별도로 보호하며 채팅이나 Git에 넣지 않습니다.
4. production 프로필은 HTTPS/CORS/Secure 쿠키/루프백/관리자/데모 비활성화에 더해 기본 프록시 포트와 네이버 콜백 출처를 검사합니다. 네이버 자격증명이 일부만 있거나 로컬 콜백을 남기면 시작을 거부합니다.
5. DB는 현재 H2입니다. 실행 중인 `.mv.db`를 복사하지 말고 [운영 문서](OPERATIONS.md)의 검증된 온라인 백업을 새 서버의 비공개 폴더에 복원합니다. 새 서버에 복원한 DB로 계정·찜·후기·다이어리 기능까지 확인합니다.
6. 저장소 원격 백업, 서버와 다른 디스크의 암호화된 DB 사본, 실패 알림 수신처를 준비합니다. 서비스 계정은 최소 권한으로 운영합니다.

## 자동 점검

로컬 프론트와 백엔드가 실행 중일 때 프로젝트 루트에서:

```powershell
node scripts/check-release.mjs http://127.0.0.1:5173
```

실제 서버에 배포한 후 승인된 운영 주소로:

```powershell
node scripts/check-release.mjs https://jiri.hknu.ac.kr --production
```

이 도구는 GET만 사용합니다. 로그인/개인정보 변경/메일 발송/수집 실행은 하지 않습니다. DB 연결, API 요청 번호, 인증 설정, 비로그인 관리자 차단, 추천 조건, 바다·카페 검색, 로그인/가입/검색의 HTML 직접 진입을 검사합니다. production 모드는 Vite 개발 HTML을 발견하면 실패합니다. 자동 통과여도 `launchApproved`는 항상 false이며 아래 사람의 검증이 필요합니다.

홈 3회와 검색어별 2회의 HTTP 시간을 분리해 기록합니다. 첫 번째 측정은 **이 검사에서의 첫 요청**이지 DB/서버 콜드 스타트를 보장하지 않습니다. 1.5초 초과는 경고이며 요청 번호로 로그를 찾습니다. 초기 색인과 대량 수집 중에는 더 느릴 수 있습니다.

## 실제 기기 합격 조건

- 휴대폰 Chrome/Safari에서 첫 접속, 검색, 상세, 뒤로가기, 새로고침, 로그아웃을 확인합니다.
- 구글/네이버 신규·기존 사용자 로그인, 취소, 만료 후 재시도, 자동로그인을 확인합니다. 인증 화면 승인과 개인정보 동의는 사용자가 직접 합니다.
- 이메일 인증의 실제 수신/스팸함/만료/재전송/잘못된 코드/가입된 이메일을 확인합니다. 설정 플래그만으로 수신 성공을 판단하지 않습니다.
- 브라우저의 `SOOMGIL_SESSION` 쿠키가 Secure/HttpOnly/SameSite=Lax인지 확인합니다. 콘솔·스크린샷에 쿠키 값은 남기지 않습니다.
- 일반 사용자의 관리자 API/다른 사용자의 수정·삭제 접근이 차단되는지 확인합니다.
- 학교 서버 재부팅 후 자동 시작, 오류 후 복구, 외부 가동 감시 알림, 새 서버에서 백업 복원을 시험합니다.

## 장애 추적

API는 서버가 만든 `X-Request-ID`를 응답합니다. 1.5초 이상 요청 또는 서버 오류는 `api_request` 로그에 요청 번호·라우트 템플릿·상태·시간만 기록합니다. DB 오류에도 같은 번호가 붙습니다. 쿼리, 실 사용자 URL, 본문, 쿠키, 비밀번호, 이메일은 이 진단 로그에 기록하지 않습니다. [OWASP 로그 지침](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

production 로그: `runtime/logs/backend.log`. 브라우저 개발자 도구 Network 응답 헤더의 요청 번호로 검색합니다. 외부 문의에는 요청 번호와 발생 시각만 전달하고 전체 로그는 공개하지 않습니다. 기존 다른 라이브러리/학교 프록시 로그는 별도 접근 제한과 개인정보 보관 정책 점검이 필요합니다.
